# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

StoryForge is a self-hosted interactive storybook running on a Jetson Orin Nano (8 GB shared CPU/GPU memory plus an 8 GB swap file, aarch64, no Docker). A local Qwen2.5-3B served by llama-server writes one page at a time, Hugging Face (or local stable-diffusion.cpp) paints a background for each page, and Piper or the browser narrates.

## Live server — teammates are using it

- Never start, stop or restart the live StoryForge (port 8000) or llama-server (port 8080) without asking first. That includes `./scripts/start.sh` and `./scripts/stop.sh`, and `stop.sh --all` is especially risky.
- To test changes, run a separate instance on port 8001 that reuses the live llama-server and loads no model of its own. Give it its own data and log folders and turn HTTPS off, otherwise it collides with the live instance's sessions, pid files and port 8443:
  ```
  mkdir -p /tmp/sf-test/{data,logs,images}
  PORT=8001 HTTPS_PORT=0 IMAGE_MODE=huggingface HF_FALLBACK_LOCAL=0 LED_ENABLED=0 \
    DATA_DIR=/tmp/sf-test/data LOG_DIR=/tmp/sf-test/logs IMAGE_DIR=/tmp/sf-test/images \
    /home/akw/jetson-ai/.venv/bin/python -m uvicorn app:app --host 127.0.0.1 --port 8001
  ```
  Stop only that process when you're done.
- Only one GPU job can run at a time, and a local picture alone takes free memory down to about 800 MB. Keep `HF_FALLBACK_LOCAL=0` (or `IMAGE_MODE=off`) on the test instance so it never runs sd-cli. Ask before generating images (including `./scripts/benchmark_sd.sh`) while the live server is busy.
- Leave the old app files in `/home/akw/jetson-ai/` alone (`app.py`, `app_backup.py`, `storyforge_app_with_illustrations.py`, the zips). The old app also uses port 8000.

## Architecture notes

- `app.py` is a FastAPI app with routes under `/api/...`. An `asyncio.Lock` allows only one page to be written at a time.
- `storyforge/config.py` defines a frozen `Settings` dataclass. Values come from `settings.env`, env vars override them (`STORYFORGE_SETTINGS` points to a different file), and numbers are clamped. `scripts/_settings.sh` loads the same file for the shell scripts.
- `storyforge/llm.py` uses stdlib `http.client` to call llama-server's `/v1/chat/completions`. Only a running summary and the latest page are sent, because llama-server runs with `-c 2048`. Prompts and the validation and repair of model replies live here too.
- Secrets (`HF_TOKEN`) live in `.env` (gitignored); everything else in `settings.env`. `config.py` reads both (env vars > `.env` > `settings.env`). Never log, print or return the token; `Settings.hf_token` is `repr=False`. Tests point `STORYFORGE_ENV_FILE` at a fake file so the real key is never used.
- Pictures are page *backgrounds only* (no characters). The hero (`/api/stories/{id}/hero`) is layered on top in the browser: the child's drawing from `/draw`, or for a story started from an idea one painted in the cloud alongside page 1 (`app._make_hero`: `images.hero_prompt` from the outline's kind, `images.cut_out_hero` removes the white paper; 20 s limit; `hero_source: "painted"`, kept off the cover). No hero (painting failed, slow or not in cloud mode): no hero layer at all, the background only; there is no placeholder. `IMAGE_MODE=huggingface|local|off`. If nothing can paint a page (and the mode isn't `off`), `ImageWorker.use_preset` shows the best-matching `static/art/preset-<place>.jpg` (castle, beach, village, space, underwater; matched by `PRESET_WORDS`) instead (`image.source == "preset"`); retrying a preset page tries real painting again.
- Cloud mode (`storyforge/hf_images.py`): FLUX.1-schnell via the `nscale` provider at `router.huggingface.co/nscale/v1/images/generations` (the `hf-inference` provider returns 410 for this model). Each page's JSON starts with a plan (`setting`, `visual_details` 2-3 items, `action` from `llm.HERO_ACTIONS`; a drawn hero also gets `hero_name` before the text), then the text is written from it. `llm.extract_plan` spots the finished plan mid-stream, so the background (setting + details) starts while Qwen is still writing; 20 s limit, then local fallback once the page is ready. Cloud backgrounds are requested at `images.oversize` (512 -> 576) and `images.crop_edges` (Pillow, in the venv) cuts 5% off every edge, where fake signatures sit, and saves a 512x512 JPEG; local sd-cli pictures are not cropped. The 3B model sometimes names characters in the plan; `images.without_characters`/`names_a_character` strip them from background prompts, so keep that filter. Backgrounds also drop every word of the hero's kind, features and name (`images.hero_words`, colours and filler excepted) and any detail about something worn or held (`WORN_OR_HELD_WORDS`), and the style is followed by `images.CLEAN` (no lettering/signature/watermark) and `images.COMPOSITION` (an open, empty centre, said positively because FLUX ignores negatives); otherwise "Cowboy Bill's hat" becomes a giant hat in a field. Stories stay gentle, but never name weapons in general prompts: the 3B model adds whatever is named. Only when the vision description itself has a weapon word (`llm._WEAPON`, checked in Python) does `llm.weapon_rule` add one "toy or tool" line. The vision prompt describes only what is clearly drawn and has no examples of any kind (examples get drawn in). The vision input stays a 512 px, tightly cropped, white-flattened JPEG: compared on saved drawings, 768 px (with or without padding) made Llama-4-Scout invent more. Each request logs image size, full prompt, model and raw answer (`hero vision request`/`hero vision answer`). The optional "Who is this?" (`who`) goes to both the vision prompt and the story (`hero_who`) and wins over the model's guess.
- `/draw` (`static/draw.*`, vanilla canvas + pointer events) posts the cropped transparent PNG and a white-backed JPEG to `POST /api/stories/drawn`, which saves the hero, gets a one-sentence description from `storyforge/vision.py` (HF router chat completions, `VISION_MODELS` tried in order; falls back to a generic description so the story still starts), stores it as `hero_description`/`character_look`, starts page 1 and returns; the browser then opens `/?story=<id>`. Gemini is not wired in: the HF vision models work with our key. Node isn't installed, so check frontend JS in a browser.
- The hero layer is animated in the browser from each page's `hero_action`: CSS keyframes in `style.css` ("Hero animation", nested `.hero-stage > .hero-move > .hero-flip > .hero-act > .hero-breath > img`) plus `static/hero.js` (line-boil SVG filter re-seeding, particles, reduced motion). `llm.HERO_ACTIONS`, `hero.js` ACTIONS and the CSS must list the same actions (a test checks). Preview all of them at `/static/hero-demo.html`. The plan's `props` (0-2 small things the hero holds, before `action` so they are known when the background starts; weapons dropped by `llm.clean_props`) become big emoji beside the hero via `llm.PROP_EMOJI` (no match: not shown), inside `.hero-breath` so they move with it (the glyph is counter-flipped, never mirrored). `app._choose_props` picks them with `llm.choose_props`: what the finished text says the hero holds or uses (`llm.held_in_text`) first, then the plan's; never anything worn (`images.WORN_WORDS`) or from the hero's own description/name (`images.worn_or_about_the_hero`). Props are re-chosen when the text completes and swapped in place in the browser (`HeroAnimator.props`) without restarting the action. `seg["prop_names"]` keeps all of them out of the background prompt. Page 1 gets the drawn hero as `llm.hero_notes` (kind + features), never the full vision sentence, or the 3B model copies it word for word.
- The reader's choice (`choice`/`custom` kinds) is softened in Python (`llm.soften_choice`), forced as the plan's first key via a JSON-schema `const` `event`, repeated as the prompt's last line ("This page must show: ..."), and checked in Python (`llm.choice_followed`); a miss gets `llm.bridge_sentence` put in front of the page already written. A page is never rewritten because a check failed (the reader is watching it stream): it is kept from 15 words (`llm.minimum_words`, counted before the repeat filter; the target comes from the story's reading level), and only a reply with no usable page is written once more. If that fails too, the longest text from either try is shown (plus the bridge sentence); the error appears only when there is no text at all. Later pages get only a 2-sentence summary (no text from the previous page, which the model retold), and `llm.drop_repeats` drops sentences mostly the same as one on an earlier page, but never takes a page under 15 words. While a page streams, only finished, already-filtered sentences are shown (`finished_only`), so nothing appears and then vanishes. Each failed check logs one `page check failed ... check=choice|length|repeat|unusable` line; unusable ones include `finish=` (`length` = cut off), tokens, `chars_before_text` (the plan's size) and words before/after the filter.
- Reading level (`story["reading_level"]`: `pre`/`early`/`confident`, default `early`; picked on the cover and `/draw`, remembered in localStorage `storyforge.level`) sets words per page (30-45 / 45-60 / 60-80), the style line in the system prompt (`llm.READING_LEVELS`), explicit limits in the page prompt (`ReadingLevel.limits`: sentences at most 8/12/18 words, Flesch-Kincaid grade about 1 / about 2 / 3 to 5; `reading.TARGETS`), the choices (pre 2 short ones, early 3, confident 3 richer ones; the schema forces the count) and, for `pre`, slower narration (ElevenLabs `speed` 0.9, browser rate 0.82), bigger text (`.words.level-pre`) and sentences over 10 words split in Python (`reading.split_long_sentences` at ", and"/"and"/"but"/commas, only before a new subject; inside `tidy_page`, so while streaming too). Every page is measured with textstat (`reading.measure`, saved as `seg["reading"]`, logged as `page reading level ... on target|OFF TARGET`). There is no `SEGMENT_MIN_WORDS`/`SEGMENT_MAX_WORDS` any more.
- Tap-a-word: the words are chosen in Python, not by the model (`reading.pick_words`): wordfreq Zipf frequency of the word or its suffix-stripped base form (rarer = harder), then syllables and length; never names (the story's or capitalised mid-sentence), stop words, words under 4 letters or unknown words; pre up to 2 words with zipf 3.5-4.5, early up to 3 below 4.0, confident up to 4 below 3.3; first occurrence only. After a page is ready, `app._definer` asks Qwen only to define those words (`llm.build_definition_messages`, schema keyed by the chosen words): pre a very short definition + one emoji, early one simple sentence, confident one sentence + a tiny example using the word; `llm.parse_definitions` skips any word that fails. It runs only while no page is being written and sd-cli is idle (`_qwen_busy`); `write_segment` cancels it (`_stop_defining`) and it is retried afterwards, so it never delays a page. The result is `seg["words"]` (word, definition, zipf, syllables, emoji/example; None = not done yet, `words_pending` in the view; 2 tries, then `[]`). The browser underlines each word's first appearance (`underlineWords`, `wordTip` in app.js) and plays `/api/stories/{id}/segments/{i}/words/{n}/audio` (ElevenLabs, cached in `data/audio/words/` by voice+speed+word+definition and shared across stories) in its own `<audio>`, pausing and then resuming the page narration; browser voice otherwise. Pre-readers can also tap any other word to hear just that word (`/api/stories/{id}/say/{word}`, only words on the story's pages). textstat 0.7.13 installs a top-level `tests` package into the venv, so the test file imports its fakes by file name (`from fake_hf import ...`).
- LED strip (`storyforge/leds.py`, firmware in `firmware/esp32_leds/`): an ESP32 with FastLED on USB serial (115200, `C,` + r,g,b x 30 + `\n`, answers `OK`; `leds.Board` releases DTR/RTS before `open()` (DTR = IO0, RTS = EN on ESP32 boards; held wrong they leave it in the bootloader, "waiting for download"), then resets it into the sketch with an RTS pulse and waits 5 s for `READY`; without it the main log says why and what the board sent. Every raw line both ways is in `logs/leds.log`). When the browser shows a page's picture it calls `POST /api/led/page {story_id, page}` (`{story_id: null}` on the cover = gentle idle glow); the background is cut into `LED_COUNT` bands top to bottom (centre 70%), k-means k=3 per band (big, saturated clusters beat gray), +20% saturation, edge-aware smoothing (only close neighbours), gamma 2.2, `LED_BRIGHTNESS` cap, ~1 s fade, on a background thread (`Strip`). No board or no permission: nothing happens (one log line with the fix command); it looks again every 15 s. Off on shutdown. Only one process can own the port (opened exclusively): the 8001 preview does; tests and other test instances set `LED_ENABLED=0`. Try a picture: `python -m storyforge.leds --image path.png`.
- `storyforge/images.py` runs a single-worker queue for local sd-cli. Each picture is a fresh `sd-cli` subprocess so memory is released afterwards (don't switch to a persistent sd-server). It checks free memory against `SD_MIN_FREE_MB` before starting, and fast mode (LCM-LoRA + TAESD) falls back to classic settings on failure.
- Keep `SD_EXTRA_ARGS` (`--diffusion-fa --vae-tiling --backend te=cpu --max-vram 0`) unless a benchmark shows a change is better.
- `data/` and `logs/` hold live runtime state (sessions, pid files, `timings.jsonl`), not source.

## Conventions

- Use `from __future__ import annotations` and type hints. Prefer the stdlib over new dependencies.
- User-facing text (UI, error messages, README) is written for non-developers: plain, friendly, no jargon.
- The frontend is vanilla JS/HTML/CSS in `static/` with no build step.
